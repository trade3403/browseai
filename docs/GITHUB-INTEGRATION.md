# V0.3 GitHub integration — development preview

## Scope
The first batch implements a GitHub App JWT signer, a narrowly scoped installation-token client, and the local authorization boundary. It does not register an app, use real credentials, expose a binding endpoint or perform automated dispatch. All contract tests use synthetic RSA keys and an in-memory HTTP transport.

## Permissions and secrets
Use a GitHub App with read-only Actions, Checks, Contents, Pull requests and mandatory Metadata. Do not grant write/admin permissions for this monitoring adapter. JWT RS256, iat backdated 60 seconds, exp five minutes in the future. The request to the fixed api.github.com installation token endpoint lists exactly one repository ID and explicitly requests read-only permissions. The response is rejected if permissions/repo/expiry differ from the expected scope; token format is opaque and never logged or persisted. The client refuses redirects and bounds time and response size. API version pinned to 2026-03-10. Reference: https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-a-json-web-token-jwt-for-a-github-app and https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app.

Private keys must be supplied through a protected operator secret mechanism in a future batch; never commit them. No real app credentials are needed for CI.

## Tenant boundary
Migration 0008 stores only installation ID, tenant ID, enabled flag and repository IDs/names, no secret. The runtime application has SELECT only with forced RLS; mapping is provisioned by a trusted operator only after independent verification, not from a user-supplied installation ID. Each installation belongs to one workspace. Before minting, resolve the authenticated user's project to an enabled mapping with matching stable repository ID and name. Actual installation ownership, allowed repository/branch revalidation, authenticated setup flow and revocation reconciliation are pending; don't treat a locally inserted mapping as independent proof of GitHub ownership. No real integration is wired into HTTP startup.

## Read-only branch observation
The internal observer derives the immutable project branch and enabled installation/repository binding from the authenticated tenant. It requests a fresh scoped token, reads the fixed GitHub repository and branch endpoints, validates repository stable ID/name, rejects disabled/archived repositories, checks exact branch name and lowercase 40-digit head SHA, then rechecks the local mapping. Only a successful observation yields a verifiedBranch and head SHA. This is an observation, not a lock or proof that the branch cannot subsequently change. No HTTP endpoint exposes tokens. GET requests refuse redirects, have a bounded response and return generic errors. Explicit rate-limit responses and 5xx return a retry deadline; no inline retry or polling worker is enabled. Installation-token rate-limit handling, pagination, independent installation ownership proof, secure operator setup and runtime wiring remain to be implemented. All new tests use mock transport; no live installation has been configured.

## Batch 3a: operator verification primitives
Protected absolute-path PEM loading (PKCS#1 or PKCS#8 RSA) and App JWT identity, installation account/target, suspension and scoped repository validation are implemented as internal primitives. Use a trusted directory and restrictive POSIX file permissions; Windows ACL support and the actual privileged provisioning command are pending. Operator approval must be independently obtained, not inferred from App access. No HTTP self-binding is exposed. No live credentials configured. CI pending.

## Batch 3b
Key loading explicitly rejects Windows until ACL verification is implemented, rejects leading non-PEM content, and has generated-key tests for both RSA encodings, unsafe paths, permissions and malformed content. Token issuance now returns the same typed retry deadline as read requests on 429, explicit rate-limit 403 and 5xx; no inline retry. The strict scoped token response contract remains unchanged pending live compatibility validation. Privileged binding persistence remains pending.

## Batch 3c
Internal provisioning service verifies remote App/account/repository before starting an atomic insert transaction. Existing installation ownership cannot be reassigned; disabled records cannot be silently re-enabled; conflicting repository mappings roll back new installation rows. Exact repeats are idempotent. PostgreSQL tests use the isolated CI owner and assert runtime-role denial, cross-tenant rejection and rollback. Production operator role, audited approval and separate CLI entry point remain pending; never supply the schema owner connection to the runtime service. No HTTP route exposes provisioning.

## Batch 3d: operator database boundary
Provision browseai_github_operator separately as NOSUPERUSER NOBYPASSRLS with no runtime or owner membership. Migration 0009 exposes only a narrow SECURITY DEFINER function; migration function owner must have access to forced-RLS tables. Successful new bindings append audit identity (session_user, tenant, App/account/installation/repository IDs); exact repeats require matching prior audit and do not duplicate it. Legacy unaudited mappings require review. Runtime and operator cannot edit audit directly. CI uses a separate synthetic operator login. The offline CLI and production ownership approval procedure are still pending. No real App credentials.

## Batch 3e: offline operator command
Run the controller executable with `github-bind bind TENANT_UUID INSTALLATION_ID REPOSITORY_ID OWNER/REPO APP_ID ACCOUNT_ID` only from a trusted operator host. Set BROWSEAI_GITHUB_OPERATOR_DSN to a verify-full TLS URI with the dedicated login, BROWSEAI_GITHUB_KEY_FILE to a protected absolute POSIX PEM path, and BROWSEAI_GITHUB_APP_ISSUER to the App issuer. Supply exactly `APPROVE TENANT_UUID INSTALLATION_ID REPOSITORY_ID OWNER/REPO APP_ID ACCOUNT_ID` on stdin followed by EOF, only after independent human verification of the tenant's ownership/authorization. Never accept tenant-generated approval as proof. The command checks database role, rejects unsafe DSN overrides, verifies remote identity and records the audited binding. No HTTP endpoint, no real secrets in CI. Windows key ACL and live App response compatibility remain unverified.

## Batch 4a: webhook verification primitive
GitHub API 2026-03-10 docs confirm scoped installation tokens and optional repository response fields: https://docs.github.com/en/rest/apps/apps?apiVersion=2026-03-10. Keep the existing strict response contract fail-closed until real App compatibility can be verified. Webhook verification uses raw-body HMAC SHA256, constant-time comparison, bounded reads, single headers, delivery UUID and positive stable IDs, with synthetic tests. Reference https://docs.github.com/en/webhooks/using-webhooks/validating-webhook-deliveries. Delivery headers are not signed; a verified event is only a polling hint, never CI success evidence. Persistent deduplication by delivery ID and body digest, tenant routing, secret provisioning and HTTP wiring remain pending.

## Batch 4b: durable delivery ledger
Migration 0010 uses a dedicated browseai_webhook role with EXECUTE only. Tenant mapping comes from enabled, audited installation/repository bindings and enabled tenants. Unique delivery UUID and SHA256 body digest provide durable deduplication including changed unsigned headers; no raw payload, token or signature persisted. Identical bodies may coalesce deliberately because deliveries are only hints for authoritative polling. Keep ledger entries until a safe retention/replay policy exists. No task transition or HTTP route is wired yet. PostgreSQL tests cover duplicate, replay, mismatched IDs, revoked binding and role denial. Migration owner must have access to forced RLS tables. CI pending.

## Batch 4c: isolated HTTP receiver
Run `controller github-webhook` as a separate process with BROWSEAI_WEBHOOK_DSN (dedicated browseai_webhook login, sslmode=verify-full), BROWSEAI_WEBHOOK_SECRET_FILE (protected absolute POSIX file containing 32–4096 printable ASCII bytes, no newline), and optional BROWSEAI_WEBHOOK_ADDR (default 127.0.0.1:8081). Reverse proxy must terminate HTTPS and forward only POST /webhook/github; configure edge rate and connection limits. Receiver has eight concurrent request slots, bounded HTTP and SQL deadlines, no tenant-facing routes, and uniform 202 after ledger handling. Invalid signatures never reach persistence. This is concurrency limiting, not a per-IP rate limiter. No actual GitHub webhook configured; polling consumption and reconciliation remain pending.
