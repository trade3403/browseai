# V0.2 PostgreSQL foundation

Migration 0001 creates the browseai schema, tenant/user/membership/session tables,
projects/tasks/stages and global repository-ID + branch leases. Application role
is provisioned separately: NOSUPERUSER, NOBYPASSRLS, not a schema/table owner and
not a member of an elevated role. CI uses a NOLOGIN role through SET LOCAL ROLE
on an isolated PostgreSQL 16 service; it is not a production login configuration.

The trusted application must derive tenant identity from authenticated server
state and set browseai.tenant_id with a transaction-local parameterized
set_config call. RLS is not a defense against arbitrary SQL execution by the
application role, nor a substitute for service authorization. Do not grant
database access to end users. The task role has no direct identity/session table
privileges. Authentication role, password hashing, session revocation, API
persistence and transactional state-machine/lease operations are not wired yet.

Migrations are run by a separate owner. The initial down migration drops the
schema and data: only for disposable CI or approved backup-backed rollback.
Never run it as an automatic production startup action. PostgreSQL 16 is the
chosen development baseline; runtime Compose remains the explicit V0.1 mock
until authenticated persistence is connected.

The global lease primary key prevents cross-tenant simultaneous rows. Fencing
tokens increase via a global sequence; an expiry timestamp alone cannot grant
ownership. Actual renew/release/fencing enforcement and reconciliation must be
implemented in the trusted service; raw SQL tests establish constraints only.
Generic conflict responses must hide the holder's identity.

CI applies up, seeds two synthetic tenants, tests default-deny/read/write/FK
isolation, revision comparison, identity-table denial, concurrent global lease
insert, fencing progression, then down and up again. No real accounts or secrets.

## 0002 session authentication foundation
Provision separate browseai_auth role (NOSUPERUSER NOBYPASSRLS, no elevated membership). Apply 0002 after 0001, roll back in reverse order. The auth pool may execute only issue_session, resolve_session and revoke_session, not read credential/project tables directly. SECURITY DEFINER functions are fully schema-qualified, with restricted search path and PUBLIC execution revoked. Use a separate non-superuser migration owner in production. The trusted credential verifier must authenticate before issue_session; the function validates active membership, but does not verify passwords. Tokens are 32 random bytes, URL-safe encoded, stored only as SHA-256 digests, expire in eight hours. Resolve rechecks current membership and enabled flags; revocation blocks subsequent resolution. Account disabling must additionally revoke sessions and leases in the future admin service; currently re-enabling an account could reactivate an otherwise unexpired session. Runtime driver/bootstrap, credential verification and HTTP endpoints remain unimplemented. No real account is used in CI.

## 0003 credential verification and authenticated preview
The auth role additionally executes login_candidate(text), which returns a password hash only to the trusted verifier and only for a unique enabled membership. Hashes use Argon2id v19, 64 MiB, 3 iterations, parallelism 1, 16-byte random salt, 32-byte output. No public registration or default account. Provision via trusted administration; offline hashPassword helper is not yet a CLI. The authentication-only controller mode requires BROWSEAI_MODE=authenticated, BROWSEAI_AUTH_DSN (postgres URL with browseai_auth role and sslmode=verify-full), BROWSEAI_ORIGIN (external HTTPS origin), and loopback LISTEN_ADDR behind a trusted TLS proxy. It fails startup if DB role/schema invalid; no mock project endpoints are available. The current Compose still starts the mock, not the authenticated stack. CI uses disposable isolated PostgreSQL with TLS disabled only for test connections, not runtime startup. Real login/session integration is tested with two synthetic tenants. Password rotation/re-enable revocation and account provisioning, full proxy/deployment support, project/task APIs and browser login UI remain pending. Production dependency audit and upgrades remain required.

## Project CRUD preview
Authenticated mode now also requires BROWSEAI_APP_DSN for a separate browseai_app login (sslmode=verify-full). Project endpoints use a server-derived principal and transaction-local tenant setting plus explicit tenant filters. GET /api/projects returns at most 100 projects with next_cursor; GET /api/projects/{id}, POST /api/projects, PATCH /api/projects/{id} (name and revision), DELETE /api/projects/{id}?revision=N. Repository ID/name/branch are configuration only until verified GitHub authorization in V0.3; they are immutable in this preview. Project deletion with tasks is rejected. Admins have no default private project access. Full-suite coverage >=75% is enforced in the mandatory database job with actual PostgreSQL integration, rather than treating SQL functions as untested in the unit-only coverage measure. No real deployment yet.

## Task CRUD and persistent state transitions
GET/POST /api/tasks, GET/PATCH/DELETE /api/tasks/{id}, POST /api/tasks/{id}/pause and /stop are available in authenticated preview. Create accepts project_id, name, stages (id and positive weight), optional max_repairs (default 5), and creates task plus stage rows in one transaction. List supports after and project_id. PATCH changes name only and requires revision; DELETE requires revision and is restricted to pristine QUEUED drafts at revision 0. State changes take row lock and CAS revision, store actual taskSnapshot fields; HTTP only exposes pause/stop with revision and never accepts trusted evidence. Resume/approve remain unavailable until reconciliation and approval adapters exist. Create idempotency, full stage configuration/commands, audit/outbox and transactional leases remain pending. No browser dispatch is enabled.

## Internal branch leases
leaseStore acquires one global stable repository ID + exact code branch lease for a queued task at the expected revision. The trusted caller must first verify GitHub authorization and identity (adapter pending V0.3). Lease duration is 60 seconds using database time, renewal is same-fence only, expired rows are not automatically replaced. Release requires inactive task state plus trusted reconciliation; stopping or pausing alone does not establish external writer termination. The ready, prepare, confirm_sent and repair persistence paths check the current live fence inside the task transaction. No HTTP lease routes, external write fencing, automatic recovery or browser dispatch are implemented. Tests use synthetic repo IDs and real isolated PostgreSQL connections.

## Mutation idempotency, audit and durable events (0004)
All project/task POST/PATCH/DELETE routes now require one Idempotency-Key header (1–128 ASCII letters, digits, underscore or hyphen). A key is scoped to the authenticated tenant and user, and binds action, resource ID, revision and canonical decoded input. A committed duplicate returns the original result, a different request using the same key returns 409. Failed transactions do not reserve keys. Internal trusted task transitions also append audit/event metadata. Audit and event rows are append-only for the runtime app role and tenant filtered; audit/event records contain IDs, action and revision only. This is a durable event foundation, not a working delivery queue, and does not yet cover account administration or lease renewals. Cached results are limited to project/task records; retention and archival remain future work. The new migration is required for authenticated readiness; run it after 0003 and roll back in reverse order only with approved backups. CI uses synthetic data.

## Account lifecycle (0005)
Provision a separate browseai_admin login with no elevated role membership and no direct table permissions. It may execute only the three account-management functions. The controller binary accepts account provision LOGIN WORKSPACE, account disable LOGIN, account enable LOGIN, and account reset-password LOGIN with BROWSEAI_ADMIN_DSN (verify-full). Provision/reset read one password line from stdin; use a protected non-echoing input or secret pipe, never a password in CLI arguments, shell history or source code. No public registration or default password. Account changes append a separate account_audit row identified by the authenticated DB operator. Disabling/re-enabling a user or tenant and changing a password revoke all affected existing sessions permanently. Real login uses a locked password-proof recheck at issuance, avoiding stale password verification after concurrent reset. The offline operator is not a web platform-admin UI; browser/node control revocation and GitHub revocation require the later adapters. The 0005 rollback removes its audit table and safeguards: only use disposable CI or explicitly approved backup-backed rollback.

## Safe local resume and approval intent (0006)
POST /api/tasks/{id}/resume and /approve accept only revision and the required Idempotency-Key header. Public resume is restricted to a paused, never-dispatched first-stage queued draft without a lease or dispatch-related audit history. Other resumes need internal trusted reconciliation. Approval is an append-only tenant-scoped intent tied to revision, stage, live fence and actor; it does not change state or send instructions. The internal confirm_sent transition requires the matching approval plus independently trusted manual-send evidence. A revision change invalidates an old intent. V0.5 must additionally bind the exact immutable dispatch instruction and real manual confirmation; this is not a browser dispatch system. GitHub and external recovery remain later-phase work.

## Immutable stage plan (0007)
New tasks require every stage to include id, weight, instruction, dependencies (an empty list is allowed), and acceptance (at least one unique check name). Stages execute in ordinal order; each dependency must refer to an earlier stage. Instruction and check-name limits are conservative UTF-8 byte limits of 8192 and 128 respectively; the task-create JSON body is limited to 128 KiB. GET /api/tasks/{id}/stages returns the ordered tenant-scoped plan, revision and configured flag. Stage creation is atomic with task creation. Existing rows lacking a plan are retained, reported unconfigured, and cannot advance to ready/prepare/confirm_sent/repair even with a valid lease; pristine drafts may be deleted and recreated. Plans are immutable for now. Acceptance strings are configuration, not actual CI evidence, and no automatic browser send exists. V0.3 will bind required GitHub workflows/jobs to actual evidence. Rollback drops plan fields and is destructive; use only disposable CI or approved backup-backed rollback.


## 6c-1a: verifier registry (0014; CI pending)
Dedicated offline browseai_verifier_operator registers/revokes immutable Ed25519 public keys using single-use external approval references; a distinct internal browseai_verifier_reader resolves only exact tenant/installation/repository/verifier/key identity with live authorization and issuance/current validity. Keys are unique globally (one key per repository binding), valid for at most 90 days, and rotation registers a fresh key, optionally overlapping before irreversible old-key revocation. No raw table grants; no private keys, GitHub tokens or public HTTP endpoints. The trusted offline operator must independently verify key ownership and obtain human approval; the UUID reference alone does not prove approval. Production migration function owner needs explicit access to existing forced-RLS bindings, following 0009; never grant elevated privileges to runtime logins. SQL tests run on disposable PostgreSQL on both migration passes. Go trusted lookup integration, atomic evidence consumption, production signing and deployment remain pending; raw-key signature helpers are not an authorization boundary and cannot advance tasks.


## 6c-1b: registered execution proof lookup (CI pending)
The production composite verification methods now belong to githubVerifierStore and accept verifier/key IDs and a signature, not a public key. The lookup uses the dedicated browseai_verifier_reader login and checks its role on the same SQL statement; the registry enforces exact binding, validity and revocation. The raw Ed25519 helper is purely cryptographic and is not a trust decision. Real PostgreSQL CI uses separate synthetic operator/reader logins and mocked GitHub API snapshots to verify both Push and PR, wrong roles, unknown keys, stale proof, signature tampering and revoked keys. No production verifier service or task transition exists. The future consumer must atomically recheck key/authorization and task revision; this lookup is not a durable authorization lease. Operator approval and independent verification of key ownership remain mandatory; no private key is stored.


## 6c-2a: sealed evidence ledger (0015; CI pending)
The evidence ledger binds project/task/revision, repository, workflow/run/attempt, exact push or PR identity, signed statement bytes, signature, digest and verifier key. A database insertion guard locks current task and authorization rows, checks expiry and key revocation, rejects duplicate job names/IDs, and derives insertion time. Signature and digest uniqueness and run-attempt uniqueness conservatively prohibit reuse even across task revisions. Forced RLS has no runtime policies and no runtime roles receive access. Owner-only disposable SQL fixtures validate constraints, not trusted execution. The existing v1 execution signature does not bind the task revision: task-bound proof, canonical message verification, trusted writer and atomic consumption are mandatory before opening the ledger. No task state changes or signature verification occur in SQL. Production owner access, retention, and safe rollback require separate review; rollback destroys this ledger and is for disposable CI or approved backup-backed recovery only.


## 6c-2b-1: task-bound execution proof (CI pending)
The v2 envelope uses domain browseai-ci-task-execution-v2 and signs project ID, task ID, revision, verifier ID and key ID together with the complete canonical v1 execution statement. Registered-key lookup and remote Push/PR source/identity checks precede candidate construction. The candidate retains exact signed bytes, copied signature, SHA-256 digest, observed/issued times and the earlier of the 30-second observation and 24-hour proof deadlines. The database must additionally cap expiry at the key validity limit and lock/recheck task, authorization and key before insert. The v1 execution-only proof cannot authorize a task ledger entry. No table access is opened by this batch; task existence and revision are checked by the future writer, not asserted by the envelope alone. Tests use synthetic signers, mock GitHub and disposable PostgreSQL. No live verifier or consumption is implemented.


## 6c-2b-2: scoped evidence ingestion (0016; CI pending)
Dedicated browseai_evidence_writer receives only EXECUTE on insert_github_ci_evidence; no direct table access. The trusted Go writer performs registered v2 composite verification and inserts exact signed bytes, signature and observed time. SQL derives the signed fields, computes digest, caps expiry at key validity and rechecks task/authorization via 0015. The writer is a trusted service principal: PostgreSQL does not independently verify Ed25519, so its credentials must never be exposed to clients or the tested repository. Do not enable an HTTP endpoint or production writer before trusted policy and verifier deployment. Duplicate writes fail closed; ambiguous database failures require reconciliation. No evidence consumption, task advancement or live signer is enabled. CI tests use synthetic keys/mock GitHub and real isolated PostgreSQL. Migration rollback removes the function, not existing ledger data.


## 6c-2c: sealed atomic evidence consumption (0017; CI pending)
The internal owner-only consume primitive locks the current WAIT_CI task, exact evidence row and live authorization/key rows, validates revision/SHA/digest/freshness, and writes a single consumption timestamp. No runtime role can invoke it or access the ledger. PostgreSQL integration tests exercise eight competing calls, rollback, scope/digest mismatch, stale task, expired proof, disabled repository/installation and revoked key. Consumption does not transition the task; the future scheduler must validate the independently trusted workflow policy and current remote Run/PR relationship, consume the complete required evidence set and update the task and audit in the same transaction. Never deploy a standalone consumption endpoint. The writer/consumer lock orders may cause a deadlock under contention; PostgreSQL aborts one transaction, and future scheduling must reconcile without treating an ambiguous result as success. Production verifier deployment remains outstanding. Rollback drops consumption history; only disposable CI or approved backup-backed recovery.


## 6c-3a: independent signer decision primitive (CI pending)
The signer accepts only an independently configured exact task/execution policy and a separately authenticated executor receipt. It binds the complete canonical v2 statement digest, actual checkout SHA, pinned test harness and image SHA-256, successful execution and a five-minute receipt freshness limit. The supervisor and attestation keys must be distinct. The signer has no generic signing endpoint, starts no repository processes, and has no database write credential. Unit tests exercise Push/PR compatibility, wrong checkout, pinned digest mismatches, missing/invalid supervisor signature, key identity reuse, stale snapshots and task changes. This is a cryptographic decision primitive, NOT proof that an isolated execution environment already exists: the supervisor must actually enforce immutable checkout, pinned dependencies and trusted harness outside repository control. The current module is not a deployed independent service. Real deployment, trusted policy distribution, key provisioning/revocation, hardened execution isolation and authenticated receipt transport remain blocked until that environment is provisioned. Keep task automation fail-closed/NEED_HUMAN. CI uses synthetic keys and no real credentials.


## 6c-3b-1: trusted supervisor orchestration (CI pending)
The supervisor runs through an explicitly trusted isolated-executor adapter and checks the exact checkout, independently pinned harness and image, all job IDs and required names, successful results, deadline, and fresh pre/post execution identity. Only then does it sign the existing receipt protocol; no signing keys are passed to the executor. Mock tests cover long execution, changed attempts, missing/duplicate/failed jobs, wrong digests, checkout, mutated request and Push/PR proof compatibility. The adapter and observation callback are trusted boundaries, not user or repository-controlled input; the supervisor does not yet launch an isolated VM/container or authenticate a real remote report. Production isolation, protected key configuration, source pinning at both observations, authenticated transport and revocation policy remain required. Keep automatic progression disabled. No production deployment.


## 6c-3b-2a: authenticated isolated-node client (CI pending)
The remote executor adapter sends canonical JSON over HTTPS with TLS 1.3, operator-provisioned client certificate, explicit CA trust and server SPKI pin. It disables redirects, proxies, compression and automatic request replay, bounds response size, generates a fresh 256-bit nonce and verifies a separate node Ed25519 signature over the exact request digest and execution report. The supervisor still checks checkout, harness, image and jobs. Disposable TLS tests cover request replay, wrong pin, tampering, failed jobs, redirects, oversized and malformed responses. This is the client-side adapter only; the actual trusted node handler, workload sandbox, protected key provisioning, independently pinned test harness/dependencies and authorization are not yet implemented or deployed. The test server requires a client certificate but does not validate a production client CA. Do not provision production credentials or enable automatic advancement. Never retry an ambiguous execution without reconciliation.


## 6c-3b-2b: one-shot trusted node handler (CI pending)
The node handler requires TLS 1.3, verified client chains and independently pinned client SPKI. Its TLS server configuration requires and verifies client certificates. It accepts only canonical bounded requests matching one separately provisioned exact task/run/attempt/checkout/workflow/harness/image grant; atomic admission permits only one execution even with a new nonce or simultaneous calls. Failures consume the grant and never produce a signed success. The report key remains in the handler and is not passed to the adapter; successful reports are validated against an immutable copy of the grant and signed over the request digest. Tests exercise handler authentication, unauthorized requests, concurrent admission and failed execution. The one-shot admission is in memory, not durable across process restarts; production needs a durable grant registry and reconciliation before provisioning a replacement. The handler is not launched by the controller and has no real sandbox adapter yet. Tests use synthetic TLS connection state and a mock executor, not actual isolated production execution. No automatic task progression, production credential or deployment is enabled.


## 6c-3b-2c-1: durable node admission journal (CI pending)
The node now requires a persistent Linux grant journal before any workload admission. O_CREATE|O_EXCL, file sync and directory sync are used to reserve the tenant/repository/workflow/event/run/attempt identity before execution. Partial or failed markers remain closed; no retry or cleanup is automatic. Tests use a real temporary filesystem, competing independent store instances and a reconstructed node; they do not simulate power loss. The operator must use one protected persistent local volume, secure its parents and exclude all workload access, rollback, replacement or deletion. This is not distributed consensus or a cross-host replay registry. Linux-only, no automatic production launch, no real workload isolation adapter. Production execution remains NEED_HUMAN until sandbox, durable deployment and credentials are independently verified.


## 6c-3b-2c-2a: offline sandbox launch adapter (CI pending)
The adapter accepts a separately provisioned exact execution request and a local immutable Docker image config ID. It invokes only a fixed trusted entrypoint with no pull, no network, read-only root, non-root UID, no capabilities, no-new-privileges, bounded CPU/memory/PIDs/tmpfs and no host mounts or inherited credentials. It rejects changed task/run/harness/image and failed or cancelled execution; attempts bounded cleanup if the daemon may still run a container. Tests use a mock runner, not a live daemon. IMPORTANT: the image must be independently assembled and audited so its digest binds the exact checkout, harness, dependencies and all job tests; the adapter trusts the preprovisioned mapping and the exit code of that trusted entrypoint, not arbitrary repository stdout. Image assembly/provenance verification, real sandbox adversarial testing, dedicated rootless daemon/VM, cleanup reconciliation, and independent service launch are still outstanding. Docker flags alone are not a VM-grade isolation boundary. No production signing or automatic task progression is enabled.


## 6c-3b-2c-2b-1: signed image build provenance (CI pending)
Sandbox construction and launch now require an independently pinned builder identity/public key and a signed canonical build receipt binding the exact execution request, checkout, source tree, harness, base image, dependencies, image config ID and job mapping. Provenance expires within 24 hours and is rechecked before execution. The adapter disables image healthchecks as an additional hardening measure. Tests use synthetic builder keys and mock command execution; no real image is built or deployed. The receipt is a trusted builder assertion, not independent verification of actual image contents; actual trusted build pipeline, pinned material acquisition, runtime inspection (including image-declared volumes/config), secure builder key management and adversarial sandbox testing remain mandatory. Do not allow production signing or task advancement before these are validated.
